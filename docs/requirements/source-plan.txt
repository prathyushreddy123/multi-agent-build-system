Multi Agent Product Development Plan
Architecture and implementation strategy for Prathyush Reddy
Version 1.1  |  17 September 2026  |  Updated review draft
## Recommendation
Build one orchestrator supported by a deterministic task controller, a persistent SQLite queue, and subscription-authenticated coding workers. Use established tools for formatting, linting, type checks, and tests. Keep custom code focused on coordination, routing, approvals, and recovery.
This plan consolidates our agreed requirements and the useful additions from the supplied architecture document. Version 1.1 adds project growth, controller monitoring, portable context, task-based routing, execution-mode selection, and an interactive workbench. These are proposed implementation requirements; integrations remain subject to phase 0 verification.

## Primary success measure
Optimize accepted product work per unit of subscription usage and manual attention. Track completion quality, repair cycles, elapsed time, and interventions. Fewer tokens alone is not a success if errors or rework increase.
## Design decisions retained from the review
Adopt rules-first routing, compact evidence-based handoffs, and an on-demand configuration curator. Keep the queue and task controller from day one. Defer local-model serving, LiteLLM, codebase indexing, and dedicated tracing services until measured needs justify them.

## Project and workspace isolation
Register each project with its repository, base branch, check commands, routing profile, and approval policy. Give each concurrent coding task its own branch and worktree. Record the base and resulting revisions. Worktrees separate edits but are not security sandboxes.
Integrate changes serially per target branch. If the target changes, check the proposed combined result again and invalidate approvals whose relevant code or action changed. Do not let two workers overwrite one working directory.
## Implementation strategy
Use one local controller process initially, with explicit adapter and gate interfaces. Prefer a language that fits the existing Pi extension project; finalize that choice after inspecting the current repository. Keep migrations, configuration, and contracts versioned in Git. SQLite transactions should update task state and its corresponding event together.
## Pi execution prerequisite
Pi is the desired interface, but its model execution path must be proven compatible with the no-extra-spend constraint. Do not assume a third-party provider login receives subscription allowance. If no compliant Pi path is available, present a specific interface or orchestrator alternative for review before continuing that integration. Local models remain optional.

# Task lifecycle and recovery
State
Meaning and next step
QUEUED
Recorded with scope and acceptance criteria; wait for dependencies.
READY
Eligible for assignment when project and provider capacity permit.
RUNNING
A worker owns an active attempt and reports progress.
CHECKING
Required deterministic gates run against the recorded revision.
REVIEWING
A separate review task assesses substantive changes and relevant context.
AWAITING_APPROVAL
A defined action is prepared with evidence for your decision.
BLOCKED
Missing input, unavailable subscription capacity, or unresolved dependency.
DONE
The agreed deliverable and required gates are satisfied.
FAILED
Automatic attempts are exhausted or an unrecoverable error occurred.
CANCELLED
Work stopped intentionally; partial artifacts remain available.

Normal path: QUEUED → READY → RUNNING → CHECKING → REVIEWING → DONE. Approval gates can intervene at any action boundary. Pure formatting changes may skip AI review under project policy. Implementation, merge, and deployment are separate tasks when they have different completion criteria.
## Bounded execution
Allow at most two automatic repair cycles after the initial implementation. Record each attempt and why it was launched.
Distinguish code failures from authentication, infrastructure, and quota failures. Do not spend repair attempts repeatedly retrying an unavailable provider.
Set task-specific deadlines and a configurable heartbeat threshold. Investigate a stale heartbeat before declaring failure; a long tool run may still be active.
Claim tasks atomically and assign unique launch identifiers. On restart, reconcile recorded attempts with actual processes and worktrees before launching replacements.
Never promise exactly-once execution. Check the external result before retrying actions such as publishing, merging, or deploying. Block when the outcome is uncertain.
## Scheduling
Use a global worker limit and fair scheduling between projects. A blocked task releases its execution slot once its worker is safely stopped. Dependency failures block downstream tasks without blocking unrelated projects. Preserve artifacts before cancelling or cleaning up worktrees.

# Quality gates and approval policy
Run configured formatting, linting, type checks, and relevant tests before substantive AI review. Use pre-commit plus the repository’s existing tools: examples include Ruff, ESLint, mypy, tsc, pytest, and Playwright. Add reviewdog when PR annotations become useful. Avoid installing every tool in every project.
A gate returns PASS, FAIL, ERROR, or SKIPPED, with its command, tool version, checked revision, and evidence path. A skipped required gate needs an explicit waiver. Re-run affected gates after fixes; passing an earlier revision is not evidence for the new one.

Enforce consequential actions through controller-owned capabilities or access boundaries; a prompt instruction alone is not an approval mechanism. Keep scoped credentials and project isolation in the foundation while broader security analysis is deferred.
## Two feedback loops
Task feedback: tests and independent review return actionable findings to the worker within the repair limit. Reviewers should verify evidence and avoid relying only on the implementer’s summary.
Setup feedback: an on-demand curator reads recurring failures and configuration, proposes a Git diff on a separate branch, and evaluates the proposal on representative tasks. It cannot activate changes itself. Track accepted and rejected suggestions to avoid repeated unhelpful proposals.
## Future security extensions
Add secret scanning, dependency checks, static security analysis, and deployment policy through the same gate contract. Candidate tools include Gitleaks and Semgrep Community Edition. Security gates can later become mandatory per project without redesigning task states.

## Evidence and accounting
Use project, task, attempt, and event IDs consistently. Record raw reported usage separately from any derived estimate. Do not label an API-equivalent estimate as subscription spend or remaining quota. Unknown measurements stay unknown. Do not store credentials in logs.
Keep SQLite authoritative. Store larger artifacts and logs as files referenced by task records. Define retention and backup settings before using the system for client work. Initially retain failed-run evidence and completed-task summaries; confirm a practical retention period during setup.
## Productivity evaluation
Use the same small feature, bug fix, research task, and complex change to establish a baseline. Compare accepted outcomes, interventions, repair cycles, elapsed time, and reported usage. Add new components only when the comparison shows a useful improvement or resolves a demonstrated reliability gap.
## Deferred components
Local models, LiteLLM, embeddings, whole-repository indexes, SonarQube, dedicated trace servers, and remote worker infrastructure are outside v1. Revisit local models only after hardware and task-quality evaluation. Revisit remote execution when local capacity or availability becomes the actual constraint.

## Monitor the decision maker and the controller
A non-LLM health check must distinguish an idle orchestrator from an unhealthy controller. Record controller heartbeat, uptime/restarts, event-loop delay, database errors, queue depth and oldest ready-task age, task claim age, and worker-slot utilization. Record orchestrator decision duration, provider errors, invalid plans, routing overrides, and repeated replanning.
Break latency into queue wait, planning, worker execution, tool checks, review, and approval wait. Show the longest stage and its reason. A human approval wait is not a model bottleneck. Use configurable timeouts and alert thresholds derived from early baseline runs.
## Recovery and backpressure
Use a process supervisor compatible with the WSL environment to restart the controller after a crash. Reconcile outstanding work before scheduling new attempts. If SQLite is unavailable, stop dispatching rather than lose task ownership. Throttle new work when machine resources or provider capacity are constrained. WSL shutdown pauses local execution; v1 does not promise continuous availability.
## Additional acceptance checks
Register many inactive projects while running two active ones. Confirm inactive projects consume no model calls, the active-project limit holds, and neither active project starves. Stop the controller, introduce a database error, and simulate slow planning; the UI must identify each condition and preserve recoverable state.

# Portable context and continuity checks
Cross-provider continuity will use project-owned records rather than depend on a provider conversation being transferable. A handoff can preserve explicit facts and evidence, but cannot transfer hidden reasoning or guarantee identical behavior between models.
Context layer
Contents and ownership
Project record
Goal, requirements with stable IDs, constraints, approved decisions, interfaces, project terminology, and known issues. User-approved decisions remain authoritative.
Task record
Scope, acceptance criteria, dependency outputs, relevant files and revision, completed steps, unresolved questions, and current gate results.
Handoff packet
Versioned snapshot of required constraints, task progress, changed files, evidence references, unresolved issues, next action, and source revisions.
Artifact store
Diffs, test logs, research sources, review findings, and full attempt logs. Fetch relevant portions on demand.
Retrieval manifest
Exact records and versions supplied to the worker, omitted optional material, token estimate where available, and retrieval reasons.

## Fetch and save strategy
Build context deterministically from project, task, role, and dependency IDs. Include mandatory constraints verbatim; retrieve relevant source files and evidence by explicit reference. Start with file search and structured metadata. Embeddings are optional later. Budget each packet for the selected model, removing redundant logs before authoritative requirements.
Save structured checkpoints after meaningful task milestones and before planned provider changes. Each checkpoint cites the base/result revision and source records. A worker may propose changes to project facts; the controller validates their schema and provenance, and material decisions require approval. Do not let a generated summary overwrite the authoritative record.
Switch at task or attempt boundaries. Build a fresh packet from current state, record what was sent, and have the receiving worker identify required constraints and next steps. Resume an existing provider session only if its adapter supports it and its stored state still matches the task. Avoid repeated switching that rebuilds context unnecessarily.
## Diagnose context loss through observable signals
Check that every mandatory requirement ID is present in the packet; flag missing, stale, or conflicting revisions before execution.
Track requirements addressed by output and tests; flag previously rejected approaches repeated without explanation.
Show compression events, dropped optional records, re-fetches, repeated questions, and requirement violations in a context-health view.
Treat acknowledgments and model self-reports as weak signals. Independent review and acceptance tests provide stronger evidence of behavioral continuity.
Do not show a fabricated context-loss percentage. Report measurable coverage and warnings. Test handoffs in both provider directions using fixed tasks with known constraints; compare violations, repairs, and acceptance with a same-provider baseline.

# Routing tools and execution mode
Route by a task profile: role, language/domain, complexity, ambiguity, required tools, context size, change risk, and urgency. First filter eligible harnesses/models by subscription access and capabilities. Then apply configured role defaults, task-specific evaluation results, current availability, and effort settings. Explain the selection in the task record.
## Learn model strengths from your own work
During phase 0, evaluate available models on a small representative set: implementation, diagnosis, architecture, research, and review. Score correctness, supported findings, acceptance-test success, repair count, duration, and usage where reported. Publish a versioned task-class-to-model map. Initial assignments remain provisional until this evidence exists; do not presume one provider is best at every task.
Keep primary and fallback models per task class. Start with explicit rules; do not add an LLM routing call for every simple task. The orchestrator resolves ambiguous assignments, and the controller enforces the eligible choices. Curator-proposed routing changes require evaluation and approval before activation.
## You do not need to manually route individual tools
A project onboarding command inspects repository manifests, existing scripts, CI configuration, and installed tools, then proposes a small quality profile. Reuse project commands where present. You review unusual installs or material configuration changes once; the controller subsequently runs the configured commands automatically.
For example, a Python feature task invokes its registered formatter, linter, type checker if configured, and tests after editing. Their exit codes and structured reports become gate results. Only a failure needing interpretation or repair invokes a model. Commands, timeouts, working directories, and parsers are registered explicitly; the scheduler does not invent shell commands from arbitrary text.

## Handle feedback without losing work
A UI comment becomes a durable feedback event. Questions trigger a response; actionable requests create a scoped revision proposal or follow-up task. Changes affecting active work take effect at a safe checkpoint, or require cancellation and replanning. Show pending versus applied feedback. Invalidate affected gate results and approvals when relevant content changes.
The browser calls the controller, which validates record versions and permissions. Bind to localhost, protect mutating requests, and render artifacts safely.
## Two responsibilities in one deliverable
The orchestrator uses an LLM for goals, plans, ambiguity, and explanations. The controller uses ordinary code for queues, timers, validation, gates, and approvals. They can ship in one package while retaining distinct responsibilities, reducing model calls and enabling recovery when the model is unavailable.
